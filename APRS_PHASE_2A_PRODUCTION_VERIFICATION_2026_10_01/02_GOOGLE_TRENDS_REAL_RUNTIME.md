## 2. Forensic Probe Results

### A. Live Adapter Execution
When invoked via `GoogleTrendsAdapter.fetch_signals("under sink organizer", geo="IN")`:
- **Network Request:** Sent via `pytrends` to `https://trends.google.com/trends/api/explore`.
- **Response Received:** Google servers returned HTTP 429 (`/sorry/index?continue=...` — `too many 429 error responses`).
- **Internal Engine Action:** Underlying `RealGoogleTrendsEngine` attempted fallback to `google_suggest_live`.
- **Authenticity Gate (Anti-Hallucination):** The adapter inspected `trend_data.get("source")`, detected `google_suggest_live`, and **strictly rejected the synthetic data**.
- **Signals Returned:** `0` records (NO fake numbers, NO hardcoded `50.0`).
- **Health State:** Status transitioned to `DEGRADED (1 errors)`, `is_healthy: False`, `last_error: "UNAVAILABLE: Google Trends direct data unavailable (returned google_suggest_live)"`.

### B. Runtime Connection
- When `web/app.py` runs a niche scan, it invokes `tools.google_trends_realtime.get_trends_engine()` directly, bypassing `GoogleTrendsAdapter` and `ResearchSourceRegistry`.
- When `core/background_daemon.py` runs an autonomous cycle, it does NOT invoke `GoogleTrendsAdapter` or `ResearchSourceRegistry`.
- Evidence generated by `GoogleTrendsAdapter` is therefore **not triggered during normal APRS runtime operations**.
