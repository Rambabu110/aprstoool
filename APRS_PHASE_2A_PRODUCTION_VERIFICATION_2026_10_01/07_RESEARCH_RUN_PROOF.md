**Audit Date:** 2026-10-01

**Auditor Roles:** Senior Software Architect + Forensic QA Lead + Production Integration Auditor  
**Scope:** Research Run Lifecycle, Run ID Association, and Source Participation

## 1. Executive Summary

The audit standard requires:
> "Inspect the research run generated by the real operation. Verify: run ID, status, start time, end time, source participation, products processed, errors, evidence counts. Prove Google Trends and GDELT are actually part of the run."

---

## 2. Research Run Architecture & Database Schema

The `research_runs` table schema in `core/database.py` (lines 765-778):
```sql
CREATE TABLE IF NOT EXISTS research_runs (
    research_run_id TEXT PRIMARY KEY,
    run_status TEXT DEFAULT 'IN_PROGRESS',
    sources_consulted_count INTEGER DEFAULT 0,
    signals_generated_count INTEGER DEFAULT 0,
    errors_json TEXT,
    summary_json TEXT,
    started_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMP
);
```

### A. Lifecycle Implementation in `ResearchSourceRegistry.execute_phase2a_run()`
In `core/research_sources/registry.py` lines 276–310:
1. `run_id = start_research_run()` initializes a new row with `run_status = 'IN_PROGRESS'`.
2. Queries Google Trends and GDELT via `fetch_phase2a_signals()`.
3. If signals are returned and a `product_id` is supplied, calls `persist_evidence_to_db()`.
4. Gathers errors from `google_trends.last_error` and `gdelt.last_error`.
5. Calls `complete_research_run()`:
   - `sources_consulted_count = 2`
   - `signals_generated_count = len(evidence)`
   - `errors = errors`
   - `status = "COMPLETED"` (if evidence > 0) or `"PARTIAL"` / `"FAILED"`

### B. Background Daemon Research Run Lifecycle
In `core/background_daemon.py` line 247:
- The autonomous background daemon calls `start_research_run()` and `complete_research_run()`.
- However, inside that loop, it only executes `orch.discover_and_evaluate_products()` and `universal_scraper.scrape_all_marketplaces()`.
- It **does NOT invoke `execute_phase2a_run()`** or `fetch_phase2a_signals()`.

---

## 3. Production `research_runs` Table Inspection

An inspection of `data/research_engine.db` reveals:
```sql
SELECT research_run_id, run_status, sources_consulted_count, signals_generated_count, started_at, completed_at
FROM research_runs;
```

**Result:**
- Total runs: **8** (all from historical APRS V7 background runs or seed scripts).
- In those 8 runs:
  - `sources_consulted_count` was logged as 0 or 1.
  - Zero runs recorded participation of `google_trends` or `gdelt`.

---

## 4. Forensic Verdict

`ResearchSourceRegistry.execute_phase2a_run()` implements the complete `start_research_run()` → `complete_research_run()` lifecycle correctly. However, because the production runtime (`core/background_daemon.py` and `web/app.py`) does not call `execute_phase2a_run()`, neither Google Trends nor GDELT participates in actual background research runs.
